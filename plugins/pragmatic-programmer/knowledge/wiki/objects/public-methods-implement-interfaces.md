*Elegant Objects* (section 2.3) makes interfaces the main tool for decoupling objects, and makes maintainability the first concern, above performance (p. 51). Decoupling here means being able to change an object without changing the objects connected to it.

## Rule

A well-designed class has no public method that does not implement at least one interface: «удостоверьтесь, что все публичные методы класса реализуют какой-то интерфейс.» (p. 52). Collaborators hold the interface type. In the book's example, `Employee` holds a `Cash`, not a `DefaultCash`, and so does not know or care how `multiply()` works (pp. 51-52).

The reasoning:

- **Replaceability.** If other classes call `Cash.cents()` on a concrete class directly, replacing that method's implementation later is blocked (p. 52).
- **Competition between providers.** A class exists because someone needs its services. Those services are documented in a contract, and several classes implementing the same interface compete and each can be swapped for another. The book calls this the essence of loose coupling (p. 52).
- **Coupling through an interface is the acceptable kind.** The book concedes that classes stay coupled through the interface, and that changing it changes every implementer and user. It counts this as a good thing, because it keeps the system stable against accidental change in one part (pp. 52-53).

To the objection that most interfaces would be used only once, the author replies that with proper unit tests you need interfaces to create fake objects, so each is used at least twice (p. 53). On abstract classes as an alternative, he answers that they are no longer worth using, and gives no reason on these pages (p. 53).

On mocking, the author says the practice is bad in itself and that PowerMock takes it to the extreme. Tests built on it cannot be maintained, block refactoring and get thrown away when the object changes. He calls PowerMock not a bad tool, but one to use very carefully and very rarely, almost never; if you need it, the code is badly written (p. 54). This wiki reads the "fake objects" of p. 53 as hand-written implementations of the interface, not as objects generated by a mocking framework. That reading reconciles the two answers but is this wiki's, not the book's.

Weisfeld's *The Object-Oriented Thought Process* (ch. 8) reaches a milder form of the rule from reuse. Contracts are the system's extension points: instead of binding to objects of particular classes, code can plug into any object that implements the contract (p. 168). In his Shop example, once `PizzaShop` and `DonutShop` honour an abstract `Shop`, «Приложение связано лишь с контрактом (Shop)» (p. 175); stating the contract «изолируете код от одной реализации» (p. 172). He then shows a contract alone is not enough: with one application per implementation still constructing its own concrete shop, «мы все равно находимся в такой же ситуации, что и раньше» (p. 175). His fix chooses the class at one point, by name at start-up, so adding a `GroceryShop` takes an implementation and no edit elsewhere: «Изменять программный код не понадобится» (p. 176). He also names the cost: contracts can be overused and make work somewhat harder (p. 168).

The books differ on when the interface is owed. *Elegant Objects* asks it of every public method; Weisfeld introduces it where several implementations fill one role. This wiki resolves it per setting: in a project following *Elegant Objects*, the stricter rule holds; elsewhere the dependency on a concrete class is reported where the code in view has a second implementation or a test needs a substitute, which is how the sign below is already bounded.

## Sign in code

- In a project following the *Elegant Objects* convention: a public method with no counterpart in any interface the class implements.
- A field or parameter whose declared type is a concrete class of the project's own code whose behaviour a caller could need to replace (it reaches I/O or another service, or the code in view has a second implementation). Value types of the language or a library (strings, numbers, dates, collections) are outside this sign.
- Near-identical copies of a client, or near-identical branches, that differ only in which concrete implementation of one role they construct (`testPizzaShop`, `testDonutShop`, Weisfeld pp. 171-175), where client code beyond the construction is repeated in each copy or branch. A single creation switch that only returns the new object is the factory [[polymorphism-or-type-switch]] names as the intended result. This wording is this wiki's.
- A test that needs a tool which patches constructors, static or final members in order to substitute a collaborator. This is the book's PowerMock symptom. The book says only that such code is badly written (p. 54); this wiki infers that the collaborator was not behind an interface.

This page owns a dependency typed by a concrete class. A parameter or field typed by a concrete collection class is [[iterator]]; one typed by a concrete project class is [[public-methods-implement-interfaces]]. A public method whose only callers are inside its own class, or that serves one outside caller in that caller's terms, is [[minimize-member-accessibility]] (narrow it); such a method is not reported here until it has been narrowed or found to fit the abstraction. A class used from another module, or one a test needs to substitute, takes an interface even with one production implementation (*Elegant Objects*' answer that such an interface is used at least twice, p. 53). A class with neither has no client to protect, and [[prefer-interfaces-for-polymorphism]]'s one-implementation limit decides. A base class that exists only so unrelated classes share a type is [[prefer-interfaces-for-polymorphism]]. A test that patches a member to substitute a collaborator belongs to the page that owns the patched shape: a static method is [[no-static-methods]], new inside a method is [[new-only-in-secondary-constructors]], a static field or singleton is [[global-data]], and a final or non-overridable method of a collaborator typed by a concrete class is [[public-methods-implement-interfaces]]. A test double that scripts or verifies calls on a collaborator through a mocking library, with no member patched, is [[prefer-fakes-over-mocks]].

## When not to apply

The source gives no limits in section 2.3. The items below are this wiki's own, except the smart-class item, which is the author's concession in section 2.9:

- **Plain data carriers at the boundary** (DTOs, wire records) that have no behaviour to substitute.
- **Classes private to one module**, never seen by another module and never replaced in a test. The decoupling argument has no client to protect there. The book's answer that each interface is used at least twice assumes a test needs a substitute, and where none does, the interface is one more file to keep in sync. This is also where [[know-when-to-stop]] weighs a layer no caller needs.
- **Languages with structural typing**, where any type with matching methods already satisfies a contract. There the rule reduces to "depend on the narrow contract, not the concrete type", and the explicit declaration is a language-level question decided at work time.
- **Methods inherited from the platform's root type** (equality, hashing, string form) already implement a contract.
- **A smart class** shipped with an interface to hold shortcuts derived from its methods. The author concedes, in section 2.9, that such a class breaks this rule and says the rule does not apply to it, because smart classes are auxiliary tools rather than ideal objects (p. 113). See [[small-interface-with-smart-class]].
- **A framework that dispatches to public methods of concrete classes, or a project convention for which classes get interfaces,** overrides this page at that boundary.
- **Cost when followed:** every change to an interface is a change to all its implementations and users, as the book concedes on p. 53. An interface cut too wide makes that coupling expensive.

## Repair

1. Declare an interface naming the service the class provides, with the public methods its clients use.
2. Make the class implement it and change clients' fields and parameters to the interface type. Choose the concrete class at one creation point and pass the object in, then delete the per-implementation copies of the client (after Weisfeld, pp. 175-176; the book's own mechanism, loading a class by name, is one option among several).
3. Make methods no client needs private, or remove them.
4. In tests, substitute a small hand-written implementation of the interface rather than patching the concrete class.

## Before and after

```
class Cash
  dollars: int
  public multiply(factor): Cash

class Employee
  salary: Cash        // the concrete class
```

```
interface Cash
  multiply(factor): Cash

class DefaultCash implements Cash
  dollars: int
  multiply(factor): Cash
    return new DefaultCash(this.dollars * factor)

class Employee
  salary: Cash        // the contract
```
