Waiting becomes indistinguishable from slow work. With one column, a long stay in it can mean "a reviewer has been going through it for a day" or "nobody has opened it", and the two call for different fixes. The column is also a hand-off to the person steering, so it is the one most likely to pile up when an agent does the executing.

What breaks, in order of cost:

1. **The diagnosis.** A board should show "when work is actively being worked on versus when work is ready and waiting for attention" (`wiki/work-states/active-versus-queued.md`, quoting Wester). If the waiting hides inside the active state, "a long time in that state reads as slow work when it may be no work at all". The fix then gets aimed at the wrong thing: speed up the review, or cut the wait for it to start. The page's sign is a task in an active state with nothing happening to it, or tasks spending much longer in one state than in the others with no way to tell whether they were being worked on.
2. **Time in state.** Reading this together with `wiki/work-states/distinguishable-work-states.md`, cycle time through the review column adds the queue and the review itself. Which share is which cannot be recovered from board history. That page lists active or queued as one of the distinctions a board must let a reader make, "otherwise waiting reads as slow work".
3. **The bottleneck is hidden.** Wester's sign is "large queues directly to the left" of a state (`active-versus-queued.md`). If the queue sits inside the state, it has no left side to show up on. This wiki expects the large queue to sit in front of the people reviewing an agent's work, and so the column most likely to hide it is this one. That expectation is unmeasured.

What does not break: the count of work in progress. It is set by position between the started and finished points, so one column or two counts the same (`wiki/moving-work/wip-control.md`).

Two ways to repair it, either of which passes the test:
- Split the column into a queue and an active state, or into Doing and Done sub-columns (`active-versus-queued.md`).
- Keep one column and mark the task when review starts. That works only if the marker is reliable; a stage that happens at the same point every time is better as a column than as a marker (`wiki/work-states/column-versus-attribute.md`).

Do not split further than tasks actually sit. The same page warns that extra states cost readability on a board of few tasks: "add a queue only where tasks actually sit". If history shows tasks rarely wait for review, the merged column costs little.

Review by the person steering is a hand-off. It happens in the same place and the task goes forward afterwards, so it takes a column and is not a block (`column-versus-attribute.md`, agent executor note). It also needs a written exit condition, or "reviewed" means different things to different readers (`wiki/work-states/column-doneness-criteria.md`).

These criteria do not depend on iterations versus flow (`distinguishable-work-states.md`, "Which holds under which setup"). The advice to keep the review column as its own state when an agent executes is this wiki's reading, not a source's.

Does your board have history showing how long tasks wait in this column before anyone opens them? That decides whether the split is worth making.
