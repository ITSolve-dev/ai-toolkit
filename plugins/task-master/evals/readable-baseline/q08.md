Half the tasks sitting in "In Review" for days is a sign of a queue at the handoff to a person. It does not tell you why they sit there, and it does not show that the board is wrong. This wiki treats a sign as a prompt to check, not as a finding (`wiki/reading-history/smell-is-not-a-finding.md`).

## What it tells you

- **Open work is piling up in one state.** Many started items, ages growing and few finishing is the buildup that `wiki/moving-work/starting-more-work.md` treats as the main sign of poor flow. The mechanism there is that started work which does not finish raises WIP, and everything behind it waits longer.
- **Where the wait is, if the agent does the work.** The agent-executor notes in this base read the likely cause as a wait for a person, with finished results queued for the few people steering (`wiki/reading-history/work-item-age.md`, `wiki/moving-work/percentile-intervention-triggers.md`, `wiki/showing-work/reading-a-cfd.md`). These notes are the wiki's own reading and have not been measured. Reading them together: if review is the constraint, starting another agent run raises WIP and adds nothing to throughput. The page names the input to check first as where finished work is waiting (`starting-more-work.md`).
- **The review state is doing its job as a state.** A planned review is a handoff and has a state of its own (`wiki/work-states/waiting-versus-blocked.md`). It is not a stop. With an agent executing, the base reads a review state as required (`wiki/work-states/distinguishable-work-states.md`). So a pile there says the handoff is where capacity runs out, not that the column should not exist.

## What it does not tell you

- **Why they wait.** Age counts waiting and size together and names no cause (`work-item-age.md`). A task can be old because nobody has looked at it, because it is too big to review in one sitting, or because it was reviewed and sent back and is sitting in review while being reworked. The last case is a reason to add a Fixing state when rework is common, and it is a flaw in the column if tasks stay long in review while being reworked (`wiki/moving-work/backward-movement.md`).
- **Whether the cause is review capacity or the cut of the tasks.** The base says the lever is the review queue and the cut of the work (`reading-a-cfd.md`). It also says combining small tasks is expected to save review effort, but "no source here tests that" (`wiki/cutting-work/combining-small-tasks.md`).
- **Whether it is passing-over.** If newer results are reviewed first while older ones wait, this is flow debt (`wiki/reading-history/flow-debt.md`). Overtaking is what marks it as aged and not merely large. A long-lived item that nobody overtook may simply be big.
- **Whether it is a problem at all.** The sign may be intended, or limited to one kind of task (`smell-is-not-a-finding.md`). "Half" and "days" have no threshold in the base. Read them against this project's own history, not against a number.
- **Whether "In Review" is one state.** Check whether the column mixes tasks waiting for a first look, tasks under review and tasks sent back. A column that holds several of these fails the criterion that a task enters and leaves a state at a point in time, so the age figures cannot be read (`distinguishable-work-states.md`).

## What to check, in this order

1. **Is it a person's wait?** Use the order from `percentile-intervention-triggers.md` (the order is the wiki's own). A stop marker means blocked. A review state means waiting for a person, so spend attention there before anything new starts. Later items pulled past it mean aged by order. An item that is active and running points to size or missing information.
2. **Count the queue against history.** Compare how many tasks were waiting in review over recent windows and whether new starts continued meanwhile. A rise in open items and cycle time together, with new starts continuing, is the sign of starting more work while started work is unfinished (`starting-more-work.md`).
3. **Check overtaking.** Look for results that entered review later and left it earlier.
4. **Look at the tasks.** Are they large? Several results to review at once is the same hidden stock as large unfinished items (`wiki/sizing/hidden-wip-in-large-items.md`).

## The first move, if it holds

Review the waiting results before starting new runs. Capacity freed goes to the aging item first (`percentile-intervention-triggers.md`). The wiki's cost to know: this makes new requests wait longer to start (`starting-more-work.md`).

## What would show this reading wrong

If you clear the review queue and cycle time does not improve, the constraint is elsewhere and the review pile was a symptom. For the falsifier see `starting-more-work.md`.

## Setup

The mechanism holds under both iterations and continuous flow. What changes is the clearing: with iterations, the period's end clears the queue only if unfinished work is actually returned and not rolled over (`starting-more-work.md`); under flow no calendar does, so the WIP limit is the only bound (`wiki/moving-work/wip-control.md`, referenced there, not read). Which of the two do you run?

## Outside the base

Check that no holiday, outage or one stuck reviewer explains the few days. That is general knowledge, not from this wiki.
