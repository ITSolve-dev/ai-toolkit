Not one task. Two tasks, with the decision in front of both of them; the decision becomes a third item on the board when making it takes work or sits with someone outside the project. The base states no rule for this exact case, so what follows is built from the pages cited, and the combination is this wiki's reading, not a source's.

**Why not one.** The two tasks differ in what they deliver. Merging them would also hide that both rest on the same open question. Nothing in the base asks for a merge because two tasks share a prerequisite.

**Who holds the decision decides the rest** (`wiki/ordering/sequence-versus-wait.md`):

- **The project holds it, usually the person steering: a sequence.** The decision comes first, and the page's test is that "one task must come first and the project can do it". It constrains order and stops nothing. Settle it before either task starts, and do not leave it inside either one. `wiki/task-content/conversation-moves-into-the-task.md` gives the rule: "Before an agent starts, every decision the task depends on is either made and written down, or explicitly left to the executor." Each task then states the decision as a precondition, which `wiki/ordering/independent-tasks.md` treats as an acceptable dependency, because it is stated. Where the decision is quick, this gives two tasks and no third.
- **Making it takes real work, such as comparing options:** it is a third task, a time-boxed investigation whose acceptance criteria are the questions to answer (`wiki/cutting-work/spike-as-last-resort.md`). That page is written for a task large because it is poorly understood. Using it for a shared decision is this wiki's extension. The same page warns of "a finished spike that produced no implementation task and no decision to drop the work" as a sign it stood in for deciding.
- **An outside party holds it: a wait.** Cut so the wait falls between tasks, and the dependent tasks "do not start until the outside party has delivered" (`wiki/ordering/sequence-versus-wait.md`).

**What breaks if it goes the other way.** If one of the two tasks absorbs the decision and the other silently assumes the result, the first stops mid-run for an answer. `wiki/work-states/waiting-versus-blocked.md` classes a stop for a decision from the person steering as blocked, and the task fails the charter's test that a started task can be finished without waiting. The second task then rests on an unstated assumption, the defect `wiki/ordering/independent-tasks.md` names. With an agent this is worse: it "defaults to non-interactive behavior for most issues" (quoted on `wiki/task-content/conversation-moves-into-the-task.md`, from Ambig-SWE), so it will not ask for the missing decision.

**What to check.** Can the person steering decide it now, in a sentence? Then two tasks, with the decision written in both. Does it need investigation, or someone outside? Then three, or a wait.
