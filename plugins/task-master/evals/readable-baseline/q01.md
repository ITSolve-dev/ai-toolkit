"Make the import reliable" is missing nearly everything an executor needs. The one gap it does not leave is the title itself: it is a catch-all, a quality of the whole import with no named piece of work, so it names no finishable unit. An executor that gets it as written has to pick its own list of what "reliable" means and stop where it likes. That is guessing.

## What is missing

1. **What would show it done.** "Reliable" is a graded word with no threshold. Nothing says what failure is meant, how it is checked, or when to stop. The base's rule is that a task states what would show it done, in a form someone could check, before it enters active work, and that the gate is firm for an agent (`wiki/task-content/testable-acceptance.md`). The sign it names is an adjective with no threshold ("fast", "usable", "secure"), or an outcome two readers could judge differently. A graded word is pinned by a condition on the task itself. It is not pinned by a separate task. The pinning can be a class of results that must never happen, such as "no import run loses or duplicates a row" (`wiki/task-content/conditions-of-satisfaction.md`, which calls this "defining a grade by what it excludes").

2. **What is observably wrong today.** "Reliable" implies some failure, and the task does not name it. The failure may be crashes, partial loads, duplicates, bad input handling or slowness. Each of these gives a different task. This is a fact only the requester has. Expected behaviour and the nature of the error are "task-only" facts: the executor cannot recover them from the repository, so the task must carry them (`wiki/task-content/recoverable-versus-task-only-facts.md`). File locations and how the import is built are recoverable, so they do not need to be in the task.

3. **Why it exists.** The task states no reason and no beneficiary. A reader who knows why can settle small choices the task did not foresee. A reader who has only the action cannot (`wiki/task-content/task-must-justify-itself.md`). Is it a customer complaint, a failed nightly run, or a migration coming up? Each makes a different "reliable" correct.

4. **Boundaries and non-goals.** The task does not say which import, which inputs, or whether the file format, the schema or the retry policy are in scope. An unbounded task invites work that is nearby but not requested. The base's rule is that work added only because it is near is kept only if the task needs it, and otherwise becomes its own task (`wiki/cutting-work/related-changes-temptation.md`). For an agent, the stated boundaries and non-goals are where that rule is applied.

5. **One unit.** The base's test for a unit is that, once started, it can be finished without waiting and its result is presented once. A task named by a broad quality fails this. The base's remedy is to ask for the list that "reliable" stands for, then sort each item. Items that can stand alone become separate tasks. Items that exist only inside other work travel with that work. The original catch-all card then disappears from the list (`wiki/cutting-work/compound-task-text-signs.md`, section "Catch-All Task"). Reading these together, my inference is that a reliable import is more likely a theme over several tasks than a single task. The base does not say this about imports.

## How to tell the executor is about to guess

The base's central point is that an agent does not reliably ask. In the study it draws on, models "almost never interact, even for severely underspecified inputs" (`wiki/task-content/agent-silence-is-not-completeness.md`, quoting Ambig-SWE). So an agent's silence is not a sign the task was complete. Do the check on the task text and the repository before the agent starts. The signs are these.

- **In the text, before the start.**
  - A graded word with no condition, as here.
  - Nothing states what would show the task done, why it exists, or what it leaves out.
  - Phrases that point at a conversation or at memory ("as discussed", "TBD", "the usual way", "handle edge cases appropriately"). They show the decision was left to talk, and an agent cannot collect on that (`wiki/task-content/conversation-moves-into-the-task.md`).
  - A comment or chat thread that states a decision the task's text does not show (same page, "Fact Stranded Outside the Task").
- **Test each missing fact.** Ask whether the executor could find it by reading the repository. If it cannot (what the failure is, what "reliable" means to the requester), the task is not ready. If it can (where the import code lives), the task is not held back for it.
- **In board history, afterwards.** A task finished and then reworked over a fact that was neither in its text nor recoverable from the repository, with no question raised before it finished. Also, acceptance criteria first added after the task moved to active, or edited after the agent took it with no restart or notice.

An empty field is not by itself the sign. A fact may live in the title or the description instead, and a field only fails once the workflow has reached the stage that reads it (`wiki/task-content/empty-fields.md`). The decisive check is whether the text and the brief state the fact.

## What to do instead of letting it guess

Ask the requester, and ask only what the repository cannot answer. Frame the question around expected behaviour and concrete failure, not implementation, so the person can answer it. For example: "Which failure have you seen, what should have happened instead, and how would you check it is fixed?" A question whose answer was in the code, or one the person cannot answer, is the sign it was the wrong question (`wiki/intake/clarifying-questions.md`). Then write the answers into the task, and cut the list into tasks that each pass the test in point 5.

Two cautions.
- The study behind these pages measured coding agents on stripped GitHub-style issues with a simulated user, not on boards. The signs listed are this wiki's reading, and no source tested them on a real board.
- The base says nothing specific about imports. The questions above are what its general rules imply.
