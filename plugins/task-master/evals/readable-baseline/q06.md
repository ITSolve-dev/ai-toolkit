Compare what each feature loses by waiting, not what it is worth in general, and rate that in words, not numbers. This is cost of delay (`wiki/ordering/cost-of-delay.md`). It has two ingredients, value and urgency. They are rated separately, and they "are NOT additive ... but rather they act on each other" (`wiki/ordering/cost-of-delay.md`, quoting the source). A high-value feature that loses nothing by waiting can go behind one whose value is draining.

**Procedure** (`wiki/ordering/ordering-by-value-and-urgency.md`):

1. Rate each feature's value in one of three bands. Killer: doing it makes an absolute killing, or not doing it "will probably kill us". Bonus: the middle band. Meh: upkeep. For a project with no revenue to point at, the base reads these as questions. Would leaving it undone end or badly damage what the project exists for? Would the people served notice and want it? Or is it upkeep? That translation is the base's own.
2. Rate urgency separately: ASAP, Soon or Whenever. The question is how fast the value drains while the feature waits. A date alone is not urgency (`wiki/ordering/a-date-is-not-urgency.md`).
3. Write one sentence each on what the value is and what waiting would do to it. Without those sentences, a band is an opinion that nothing later can check.
4. Ask what happens if each feature is never done. A feature that gains little but whose absence would hurt (compliance, security, keeping things running) looks last when ranked on benefit alone. A loss nobody can accept is a constraint, not a weight (`wiki/ordering/relative-weighting.md`).
5. Order by the table in the ordering page. Killer/ASAP is first and Meh/Whenever is last. The seven ranks between them are the base's own derivation, not the source's matrix. The weakest step is Bonus/ASAP against Killer/Soon, so look there first if the order turns out wrong.
6. Break ties by size. Within one rank the smaller feature goes first, and only when sizes differ a lot and work is waiting for capacity (`wiki/ordering/cost-of-delay-over-duration.md`). With an agent executing, the scarce thing is probably the steering person's attention. "Size" then means what the feature costs them to direct and review. This is unmeasured.
7. If the sizes are close, the cost of delay is the same, and neither feature unblocks the other, take either one (`wiki/ordering/incomparable-tasks.md`).
8. Write down which factor decided and when you rated. A rating describes the day it was made and has to be redone before it decides anything later (`wiki/ordering/cost-of-delay.md`).

**If you cannot rate a feature at all**, do not force a band. Ask whoever can say what it is worth, since value and urgency are facts only the task's owner holds (`wiki/ordering/incomparable-tasks.md`). If the answer depends on learning something, the first step is the smallest piece that shows it.

**Add learning and risk.** After the first order, move a feature forward if doing it settles a named risk or teaches something a decision is waiting for, and only if it will be built regardless. Move it back if it could be dropped. Write down each move (`wiki/ordering/prioritization-factors.md`).

**What breaks:** the rating is coarse, so ties are common. The evidence behind it is one practitioner article with no measurement. A single rater has nobody to challenge their bands. The bands also tend to inflate toward the top (`wiki/ordering/ordering-by-value-and-urgency.md`).

**Check afterwards.** Was the value gain you wrote down real? Did the deferred feature lose more than the first one gained? A deferred feature that keeps coming back as new requests means its value was underrated.

Neither option depends on your setup (iterations or flow, estimates or none) except the size tie-break, which needs some size on the project's own scale.
