An **Event Store** maintains a persistent, ordered record of every [[domain-event]] published within a single [[bounded-context]]. Vernon: "Consider what you could do if you were to store a discrete Event for every model command behavior that is ever executed" (raw L7528).

## Why keep one — the six benefits

(raw L7530-7542)

1. **A queue for publishing** all Domain Events through messaging infrastructure — the primary use in the book, enabling integration where remote subscribers react in their own terms.
2. **Feed REST-based notifications** to polling clients (see [[notification-log]]) — "logically the same as point 1, but different in actual use."
3. **A historical record** of every command outcome, to trace bugs in the model and in clients. Crucially, "an Event Store is not just an audit log. Audit logs may helpful for debugging, but they rarely carry the complete results of each Aggregate command outcome" (raw L7536).
4. **Business analytics** — trending and forecasting; historical data is unavailable later "Unless an Event Store is maintained from the start" (raw L7538).
5. **[[event-sourcing]] reconstitution** — rebuild an [[aggregate]] "by applying to an Aggregate instance all previously stored Events in chronological order", with periodic snapshots (e.g. groups of 100) to optimize (raw L7540).
6. **Undo** blocks of changes by excluding, patching, or inserting Events in the stream (raw L7542).

Benefits 1 and 2 are the ones Vernon implements; 3 and 4 follow for free from recording all significant Events; 5 and 6 are not pursued in this chapter.

## Implementation shape

A single-responsibility subscriber captures every Event. SaaSOvation's `IdentityAccessEventProcessor` is a Spring **AOP aspect** whose `@Before` advice intercepts all Application Service methods, then subscribes a wide-open subscriber (`subscribedToEventType()` returns `DomainEvent.class`, "all domain events") that delegates each Event to `EventStore.append()` (raw L7561-7584).

`append()` serializes the Event (JSON via Gson) into a `StoredEvent` value and saves it (raw L7595-7607). A `StoredEvent` holds `eventBody` (the serialization), an autogenerated sequence `eventId`, `occurredOn`, and `typeName` (the concrete Event class) (raw L7619-7637). Rows persist to a table keyed by an auto-increment `event_id` (raw L7644-7650).

The autogenerated, monotonically increasing `eventId` is what lets downstream consumers read Events "in the order in which they occurred" (raw L7544) and track what has already been forwarded (see [[notification-log]], [[event-driven-integration]]).

## Consistency role

Placing the Event Store "in the same persistence store that is used to store your domain model" lets the model change and the Event be recorded "under the same local transaction" — the third of Vernon's messaging-consistency options (raw L7488) — avoiding XA two-phase commit while guaranteeing the model and its Events are consistent (see [[event-driven-integration]] for all three options).

## As an event-sourcing log (A+ES)

Under [[event-sourcing|A+ES]] the Event Store is not just a publishing queue but the **system of record**: it holds each [[aggregate|Aggregate]]'s Domain Events as an append-only **Event Stream**, one stream per Aggregate instance, uniquely distinguished by the identity of the root [[entity|Entity]]. It is deliberately minimal — load a stream, append to a stream — not a general query database.

```
public interface IEventStore {
    EventStream LoadEventStream(IIdentity id);
    EventStream LoadEventStream(IIdentity id, int skipEvents, int maxCount);
    void AppendToStream(IIdentity id, int expectedVersion, ICollection<IEvent> events);
}
public class EventStream { public int Version; public List<IEvent> Events; }
```

Three design points carry the weight:

- **Identity-keyed streams.** Streams are addressed by Aggregate identity (`IIdentity`, e.g. `CustomerId`), so loading a stream reconstitutes exactly one Aggregate. The `skipEvents`/`maxCount` overload supports paging and snapshot-relative loads (see [[aggregate-snapshot]]).
- **`expectedVersion` on append → optimistic concurrency.** The version returned by `LoadEventStream` is passed back into `AppendToStream`; the store rejects an append whose expected version no longer matches the stream head — "we pass a concurrency version variable from the Load() to the Append() methods" (raw L14598). This is how an event-sourced Aggregate enforces consistency under concurrent writers without locking (see [[optimistic-concurrency-control]]).
- **Layering: typed over raw.** "The class implementing `IEventStore` is a project-specific wrapper around the more generic and reusable `IAppendOnlyStore`" (raw L15120). The high-level `IEventStore` handles serialization and strong typing; the low-level `IAppendOnlyStore` deals only with `byte[]` payloads and string stream names — keeping domain-facing code strongly typed while the storage engine stays generic.

### Backing storage — strong consistency is the one hard requirement

An Event Stream is essentially an append-only list of messages serialized into byte blocks, so the backing store is almost free to choose. "This Event Store can be implemented quite easily with a relational database ... or with NoSQL store that has strong consistency guarantees (file system, MongoDB, RavenDB, or Azure Blob storage)" (raw L14459). Because it is so simple, the whole infrastructure can be moved between hosting solutions, supporting failover and cloud-outage tolerance. An eventually-consistent backing store breaks the append-and-version-check contract and permits corruption.

### Two read paths

- **Per-stream read** — "required for rebuilding the state of a single Aggregate" (replay one stream to reconstitute one Aggregate).
- **Global read (all events)** — "used by the infrastructure to replicate Events, to publish them without the need for two-phase commit, and to rebuild persistent read models such as are needed for CQRS-based user interfaces" (raw L15161). This path is what feeds [[read-model-projection|Read Model Projections]].

### Replication: write-through vs write-behind

For fault tolerance a Master Event Store can replicate newly appended events to a Clone. **Write-through (immediate)** — the Master considers events saved only after replicating them to the Clone (raw L14606): stronger durability, higher latency. **Write-behind (eventual)** — the Master saves first and replicates on a separate thread (raw L14612): lower latency, but the Clone can lag or diverge on a crash. Assuming a write-behind Clone is a durable backup is a failure mode — a crash between save and replication silently loses events.
